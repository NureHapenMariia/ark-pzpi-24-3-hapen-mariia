1 БІЗНЕС-ВИМОГИ 
1.1 Background (Передумови)
Стан шкіри залежить не лише від засобів догляду, а й від умов навколо людини: температури, вологості повітря та освітленості в приміщенні. Зазвичай людина не пов'язує ці чинники зі змінами шкіри, а звичайні нотатки в телефоні не містять об'єктивних даних про довкілля. 
Проблема важлива, бо без даних про довкілля користувач підбирає догляд навмання й не може відрізнити реакцію шкіри на засіб від реакції на умови (сухе повітря, недостатнє освітлення). Поточні підходи цього не вирішують: нотатки не містять об'єктивних вимірювань, а побутові датчики не пов'язані з доглядом. 
Програмна система моніторингу умов догляду за шкірою та впливу довкілля Lada призначена для ведення єдиного журналу: показників довкілля, що збираються автоматично, засобів догляду та добровільних спостережень користувача. Мета розробки полягає в тому, щоб користувач бачив зв'язок між умовами та власними відчуттями й міг свідомо коригувати свій догляд. Система не ставить діагнозів і не замінює консультацію лікаря.

2 КОНЦЕПЦІЯ РІШЕННЯ 
2.1 Опис призначення системи (Vision Statement) 
Для людей, які хочуть зрозуміти, як довкілля впливає на їхню шкіру, Lada є системою моніторингу, що автоматично збирає температуру, вологість та освітленість за допомогою датчика ESP32, поєднує їх із записами про догляд і спостереженнями користувача та показує закономірності в Android-застосунку й вебклієнті. На відміну від окремих датчиків і звичайних щоденників, система об'єднує об'єктивні дані та особистий журнал в одному місці, а фото й добровільні спостереження зберігаються лише за згодою користувача. 
Цінність для користувача: він бачить, як температура, вологість і освітленість співвідносяться з його відчуттями та доглядом, отримує нагадування в зручний час, може отримати відповідь на питання з перевірених інструкцій і зберігає контроль над власними даними. 
2.2 Опис бізнес-логіки 
Користувач працює із системою за таким процесом: 
1) Реєстрація. Користувач створює профіль, надає згоду на обробку даних і, за бажанням, окремо на збереження фото. 
2) Підключення датчика. IoT-клієнт прив'язується до профілю (на етапі розроблення його роль виконує емулятор). 
3) Сесія вимірювань. Користувач починає сеанс; IoT-клієнт із заданим інтервалом зчитує температуру, вологість і освітленість, перевіряє діапазони й передає дані на сервер по Wi-Fi (HTTPS) або на телефон по BLE. 
4) Обробка даних. Сервер відсікає дублікати, зберігає вимірювання й рахує добові агрегати. 
5) Ведення журналу. Користувач вносить засоби догляду та спостереження (фото за згодою), зокрема без інтернету; записи синхронізуються після появи зв'язку. 
6) Нагадування. Сервер за правилами користувача надсилає push-нагадування про догляд. 
7) Аналіз. У вебклієнті користувач порівнює умови довкілля за днями й бачить свої записи поруч. 
8) LLM-помічник. Користувач ставить запитання, система шукає відповідь лише в дозволених інструкціях догляду, або формує підсумок щоденника за вибраний період. Відповіді позначені як не медична рекомендація. 
9) Керування даними. За запитом користувача його дані видаляються. 


Основні бізнес-правила: система не ставить діагнозів; фото зберігаються лише за згодою; LLM користується лише дозволеними інструкціями; вимірювання не губляться при втраті зв'язку. 
3 ФУНКЦІОНАЛЬНІСТЬ ТА РАМКИ 
3.1 Функціональність серверної частини та IoT-клієнта
Серверна частина виконує такі завдання:
- автентифікація та розмежування доступу до даних користувача;
- керування профілями й сесіями вимірювань;
- прийом даних по HTTPS, перевірка діапазонів значень і захист від дублювання записів;
- зберігання потокових даних, архів і розрахунок добових агрегатів;
- зберігання щоденника засобів і спостережень та фото за згодою;
- правила й надсилання нагадувань;
- надання даних для порівняння умов за днями;
- LLM-функції: пошук у дозволених інструкціях догляду та підсумок щоденника;
- приймання офлайн-записів під час синхронізації;
- видалення даних на вимогу користувача.


IoT-клієнт (пристрій ESP32) виконує такі функції:
- зчитування температури, вологості й освітленості;
- перевірка діапазонів значень;
- ведення журналу сеансів;
- буферизація вимірювань при втраті зв'язку;
- передавання даних на сервер по Wi-Fi (HTTPS) і на телефон по BLE.


На етапі розроблення покази датчиків імітує програмний емулятор у тому самому форматі передавання, що й реальний пристрій.


3.2 Функціональність вебклієнта та мобільного клієнта
Мобільний клієнт (Android) виконує такі функції:
- вхід і керування профілем;
- початок і завершення сесій вимірювань;
- зчитування даних із датчика по BLE на місці;
- ручний запис засобів догляду й спостережень, фото за згодою;
- отримання нагадувань;
- робота без інтернету з подальшою синхронізацією;
- доступ до LLM-функцій.


Вебклієнт виконує такі функції:
- перегляд і порівняння умов довкілля за днями на графіках;
- перегляд журналу засобів і спостережень;
- керування доступом;
- доступ до LLM-підсумків.


Взаємодія із сервером. Обидва клієнти працюють із сервером лише через Web API по HTTPS з автентифікацією за допомогою JWT. Мобільний клієнт додатково зв'язується з IoT-клієнтом по BLE; офлайн-записи зберігаються в локальній базі й надсилаються на сервер після відновлення зв'язку; нагадування надходять як push-сповіщення.


3.3 Рамки первинного випуску (Scope of Initial Release)
Перший випуск включає всі частини системи в мінімальному, але робочому вигляді.
Пристрій ESP32: код на C++, зчитування трьох датчиків, перевірка діапазонів значень, журнал сеансів, передавання даних через HTTPS (Wi-Fi) та по BLE. На етапі розроблення та демонстрації дані датчиків імітуються програмним емулятором; логіка пристрою й формат передавання від цього не змінюються.
Серверна частина: Web API та бізнес-логіка для профілів, сесій вимірювань, щоденника засобів і правил нагадувань; зберігання потокових даних, архів і добові агрегати; розмежування доступу; видалення даних на вимогу користувача.
Android-застосунок (Kotlin): BLE-зчитування на місці, ручний запис засобів і спостережень, фото лише за згодою, нагадування, офлайн-записи із синхронізацією.
Вебклієнт: перегляд і порівняння умов за днями, журнал засобів, керування доступом.
LLM-модуль: пошук у наборі дозволених інструкцій догляду та короткий підсумок щоденника за вибраний період.
Українська мова інтерфейсу, захист персональних даних (шифрування передавання, згода на фото та обробку даних).
4 БІЗНЕС-КОНТЕКСТ 
4.3 Опис програмних засобів та інструментів (Operating Environment)
Пристрій: мікроконтролер ESP32, прошивка мовою C++ (PlatformIO, фреймворк Arduino); датчики температури й вологості (SHT31 або BME280) та освітленості (BH1750); зв'язок через Wi-Fi (HTTPS) та BLE. На початкових етапах розроблення фізичні датчики не використовуються: їхні покази замінюються моковими (імітованими) даними, які генерує програмний емулятор і передає на Web API в тому самому форматі, що й реальний пристрій. Підключення фізичного ESP32 із датчиками заплановано після готовності серверної частини.
Серверна частина: Web API з бізнес-логікою, реалізоване мовою Python із використанням фреймворку FastAPI; автентифікація за допомогою JWT. Реляційна СУБД PostgreSQL зберігає профілі користувачів і щоденник; для потокових даних вимірювань, архіву та добових агрегатів використовується розширення TimescaleDB, для векторного пошуку по інструкціях догляду — pgvector. Фото користувачів зберігаються в S3-сумісному сховищі. Розгортання виконується в контейнерах Docker, з'єднання захищені HTTPS (TLS). Push-нагадування надсилаються через Firebase Cloud Messaging.
Мобільний клієнт: Android, мова Kotlin, Jetpack Compose, локальна база даних Room для офлайн-записів, WorkManager для синхронізації, Android BLE API.
Вебклієнт: сучасні браузери, React із TypeScript, бібліотека графіків (Chart.js або Recharts); взаємодія із системою лише через Web API.
LLM-модуль: зовнішня мовна модель, підключена через API; пошук по дозволених документах з інструкціями догляду реалізовано за підходом RAG (ембедінги та pgvector).
Системи керування версіями та середовища розробки: Git і GitHub для зберігання коду та документації (репозиторій: [посилання]). Середовища: Visual Studio Code або PyCharm (Python, FastAPI, вебклієнт), Android Studio (Kotlin), PlatformIO у VS Code (ESP32). Для тестування API використовуються Swagger UI (вбудований у FastAPI) і Postman, для автоматичних тестів серверної частини — pytest.
Наведений перелік технологій є попереднім і може бути уточнений на етапі проєктування.
Вимоги до доступності: система доступна не менше 99 % часу.
Надійність: вимірювання не губляться при втраті зв'язку (буферизація на пристрої та в застосунку).
Продуктивність: відповідь API на типові запити не довша за 2 секунди.
Цілісність: перевірка діапазонів значень датчиків, захист від дублювання записів, розмежування доступу до даних користувача.

Проаналізовано проблему та наявні аналоги, визначено призначення системи, описано бізнес-логіку з погляду дій користувача, функціональність серверної частини, IoT-клієнта, вебклієнта та мобільного клієнта, а також перелік головної функціональності з десяти пунктів. Окреслено склад первинного випуску й плани наступних версій, обрано технологічний стек (Python, FastAPI, PostgreSQL, Kotlin, React, ESP32) та засоби розроблення (Git, GitHub). Система поєднує автоматичний збір даних про довкілля, журнал догляду та LLM-помічника, що відрізняє її від наявних аналогів. Через відсутність фізичних датчиків на початкових етапах використовуються мокові дані. Описаний обсяг достатній для переходу до проєктування та реалізації.
